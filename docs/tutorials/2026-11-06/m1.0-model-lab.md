# M1.0 Model Lab — Current Shell Procedure

- Date: 2026-11-06 (UTC)
- Status: Current
- Model: `M1.0`
- Claim type: procedural model lab; no strategy, edge, or profitability claim.

This is the current end-to-end procedure for the M1.0 model surface. It uses only
the eight commands the shell exposes: `candles`, `candles-tolerant`, `timeframes`,
`events`, `report model`, `run check`, `fetch`, and `help`.

Strategy, execution, portfolio, and backtest runs are S3.x. This tutorial does
not describe them, and the pre-M1.0 manuals under `docs/roles/2026-10-29/` are
historical. The stage contract and the planned commands are in
[`docs/architecture/command-surface.md`](../../architecture/command-surface.md);
a planned command is not available from this lab until it is implemented.

## 1. Build and start

```bash
cargo build --release
./target/release/quantrule
```

A non-interactive invocation runs one command and exits with its status:

```bash
./target/release/quantrule help
```

`help` lists the command map. `help all` prints every command contract, and
`help glossary` prints the precise-term glossary. There is no `help tutorial`
command; this document is the tutorial.

## 2. Inspect candles

```bash
./target/release/quantrule candles \
  crates/quantrule-shell/tests/fixtures/three.csv
```

Expected shape: one JSON object per retained candle, with `series_index`,
`window_index`, `datetime`, `open`, `high`, `low`, `close`, and `volume`.

The tolerant variant prints NDJSON on stdout and its quality report on stderr:

```bash
./target/release/quantrule candles-tolerant \
  crates/quantrule-shell/tests/fixtures/tolerant_mixed.csv
```

## 3. Build the timeframe ladder

```bash
./target/release/quantrule timeframes \
  crates/quantrule-shell/tests/fixtures/timeframes.csv \
  > /tmp/m1.0-timeframes.ndjson \
  2> /tmp/m1.0-timeframes.report
```

Expected: NDJSON candles for every retained timeframe on stdout, then the
partial-bucket and gap report on stderr. The data engine supports 1m, 5m, 15m,
1h, and 4h; the M1.0 model ceiling is 1h.

## 4. Inspect the event batch

```bash
./target/release/quantrule events \
  crates/quantrule-shell/tests/fixtures/state_m1.csv \
  --window latest
```

Expected: one JSON object per event, grouped by timeframe and availability
order. Each row carries the event type, subtype, source, occurred bar,
available bar, direction, and measured values. The model publishes numbers and
codes; the shell adds the presentation labels.

## 5. Run the model report

Use a fresh output root:

```bash
rm -rf target/tutorial-model
./target/release/quantrule report model \
  --config crates/quantrule-shell/tests/fixtures/config-run/run.json \
  --out target/tutorial-model
```

Expected artifacts under `target/tutorial-model/model/`:

```
summary.txt
report.json
result.json
readings.csv
events.csv
levels.csv
legs.csv
provenance.json
```

`report.json` carries `model_version`, `view_contract`, `data_version`,
`requested_period`, and `flat_report`. `events.csv` carries the registered and
extended event batch in availability order. The bundle is refused if
`target/tutorial-model/model` is already non-empty.

A v1 spec adds `conditions.csv`. A `quantrule.model-spec/v2` spec adds
`prediction.csv`; it adds `conditions.csv` when conditions are declared, and
`panel.csv`/`session.csv` when those are declared.

## 6. Validate the policy and engine configs

```bash
./target/release/quantrule run check \
  --config config/examples/btcusd-2024/run.json
```

Expected: one `run ok ...` line after every config check. The command reads
no candles and writes no artifacts.

## 7. Prove the rerun is deterministic

Run the same configuration into two fresh roots and compare every artifact:

```bash
rm -rf target/tutorial-model-a target/tutorial-model-b
./target/release/quantrule report model \
  --config crates/quantrule-shell/tests/fixtures/config-run/run.json \
  --out target/tutorial-model-a
./target/release/quantrule report model \
  --config crates/quantrule-shell/tests/fixtures/config-run/run.json \
  --out target/tutorial-model-b
diff -r target/tutorial-model-a/model target/tutorial-model-b/model
```

Expected: no output from `diff`; the two bundles are byte-identical. The same
candles, data version, and configuration produce the same artifacts.

## 8. Optional source fetch

`fetch` is the only network path. It is optional for the lab and does not change
the model procedure:

```bash
./target/release/quantrule fetch gold 2025-01-01 2025-12-31 \
  --timeframe 1h \
  --csv data/sources/XAUUSD_H1.csv
```

The CSV is written through a sibling temporary file and renamed only after every
row is accepted.

## 9. Role handoff for model work

| Role | Current model-lab responsibility | Handoff |
|---|---|---|
| Quant Researcher | States the measurement question and the pre-registered protocol; chooses the model spec and partitions | Approved protocol and config |
| Quant Developer | Implements or changes the model only within the approved protocol; runs the causal, determinism, golden, and edge-case tests | Reproducible run and deviation report |
| Quant Validator | Reproduces the bundle from the recorded data version and config; checks causality, availability, costs, and fixtures | Validation record and residual risks |

The model lab ends at the model result. A model result is not a strategy edge,
and a single run is not validation.
