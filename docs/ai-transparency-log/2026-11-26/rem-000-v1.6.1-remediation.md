## 3. Verification and limitations

Reproduction commands were read-only: `git status`, `git tag`, `git log`,
`gh issue list`, `gh pr list`, `gh release view`, `rg`/`grep`, `sed`, and
`jq` over the recorded JSON. The plan was staged and checked with
`qr-governance check --all`; the first run failed because the section was titled
`## 10. Verification matrix` instead of the required `## Verification table`.
The heading was corrected and the second run returned `governance check ok`.
No test result is claimed. The plan's verification table starts every row at
`Pending`; observed evidence is filled only after execution.

The single-laptop constraint is recorded as an explicit accepted-risk path for
HA-22/23 and RR-07. The signature is an accepted risk unless the operator
supplies the offline key and `cosign`. The 72-hour soak is capacity-gated; it
must not be shortened or simulated.

## 4. Learning

- The `v1.6.0` release note is honest about its HA boundary; the defect is the
  plan status and the contract-only v5/lineage paths, not a concealed claim.
- The strongest remediation is to make run v5 resolve at submission, commit
  lineage with the run row, and let the worker consume a resolved bundle once.
- Real HA cannot be produced from one laptop. It must be an accepted risk, not a
  test that is quietly skipped.
- The proposed plan deliberately separates decisions (v1.5.3, MinIO, strategy
  crate, signature, independence) from implementation so the human can approve
  or reject each without blocking the rest.
- No test, gate, or release evidence was invented. The plan uses `Pending` until
  a real command produces a result.
- The governance checker requires the exact heading `## Verification table`; a
  numbered heading is rejected. This is a useful mechanical constraint for the
  next plans.
