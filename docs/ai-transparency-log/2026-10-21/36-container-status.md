- **Learning:**
  - **The agent wrote a rule and the human corrected it, and the correction was the better rule.** The reasoning that produced the old one was consistent — a container must not sit in the single `In Progress` slot beside the child being worked — and it produced a board that misread. A parent titled "build the model engine" reading as done above fourteen open children is wrong in a way that no amount of internal consistency protects against. The lesson is recorded in the plan for issue #36 and in the log for issue #14, so the reasoning is not repeated.
  - **A rule that couples two things the human did not ask to couple leaves a state nobody can reach.** Marking a board item `Done` closed its GitHub issue through the board's own workflow. The container was then both closed on GitHub and in progress on the board, and the only way back was to reopen the issue by hand. The new rule keeps the coupling, because it is the board's behaviour, and the automation in issue #37 reopens a container whose child reopens.
  - **The built-in workflows already answer the question the screenshot was about.** An issue closed on GitHub marks its board item `Done`, with no code and no credential. What no built-in does is recompute a container's status from its children, and that is the one thing the human's rule needs. The division of labour that follows is that the built-ins own the `Status` field, the repository workflow owns the custom fields and a container's status, and the agent owns a leaf's `Todo` and `In Progress`.
  - **The rule alone cannot cover the human's own actions.** The agent updates the board as part of the work, so every transition it makes is covered. A sub-issue closed in the browser is not, and the parent stays stale — the state the human corrected by hand today. The workflow exists for that one gap, and the rule names it so the gap is stated rather than hidden.
  - **Rejected:** rewriting the two transparency logs instead of appending to them. A log is a record of what was decided and what was done at the time; the earlier entries stand, and the change is a new entry beside them.
  - **Rejected:** leaving issue #14 closed and letting the automation reopen it. The repair belongs with the rule that makes it necessary, and the automation lands in a later work item that depends on a credential the human has not created yet.
