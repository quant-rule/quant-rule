## Entry — 2026-10-21, the container rule replaced

- **Date and tool:** 2026-10-21 (UTC; 2026-10-20 local time). opencode (MiniMax M3.1 Flash), running in a local shell with `git`, `gh`, and filesystem tools.
- **Intent and boundary:** Record that the container rule this log's entry added was replaced by the human, and that the board's maintenance is to be automated rather than done by hand. The boundary is this log, the execution plan beside it, and the rule in `AGENTS.md` section 9; the automation itself is issue #37.
- **Verification and evidence:**
  - This log's entry recorded the container rule as "a container is `Done` when its own deliverable is delivered". The human replaced it: a parent's status follows its children.
  - The project's seven built-in workflows were read through the API, and GitHub's documentation for the built-in automations was consulted. The built-ins set the `Status` field only. They mark an item `Done` when its issue is closed, they close the issue when the item is marked `Done`, and they set `Todo` when an item is added. None of them recomputes a container's status from its children, and none of them touches the custom `State` or `Item type` fields.
  - GitHub's documentation states that `GITHUB_TOKEN` "is scoped to the repository level and cannot access projects", and recommends a GitHub App for organization projects. The permission list for `GITHUB_TOKEN` was read and holds no `projects` permission, which confirms it.
  - The API shapes the automation relies on were read directly: `Issue.parent`, `Issue.subIssues` with each sub-issue's state, the `reopenIssue` mutation, and the project's `Status`, `State`, and `Item type` fields with their option ids.
- **Learning:**
  - **The built-in workflows already cover the case the screenshot was about.** An issue closed on GitHub marks its board item `Done` with no code and no credential. What no built-in covers is a container's status following its children, and that is the one thing the human's rule needs.
  - **A rule that only an agent can enforce is a rule that breaks when the human acts.** The agent updates the board as part of the work, so every transition it makes is covered. A sub-issue closed by the human, in the browser, is not, and the parent stays stale — which is the state the human corrected by hand. The workflow closes that hole, and the rule becomes the specification it enforces rather than a chore.
  - **The evidence about what a built-in does is not in the API.** A workflow's configuration is not readable through GraphQL, and its action has to be confirmed in the browser. What the API did show is enough to reason about the division of labour: the built-ins write the `Status` field, the custom fields are untouched, and the agent has been writing them by hand.
