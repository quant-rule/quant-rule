- **Learning:**
  - The human's report and the API's view of the world disagreed, and the disagreement was the whole problem. The data said the issues were on the board, unfiltered and unarchived; the human said they were not there. The resolution was not to argue the point but to remove every reason the two could disagree: a field that says which kind an item is, a second signal in the labels, and a view that was missing its configuration entirely.
  - The board was never a static list. Six engine issues and this change's own issue arrived on it during the work, and GitHub's automation adds each pull request to it as it is opened. Any verification that hardcodes an item count is wrong within minutes. The verification therefore reads the count and the values back and asserts against the kind of each item rather than against a remembered list.
  - The API's error message was more useful than its schema. "Roadmap views do not support visible fields" says plainly that a roadmap view is configured in a different way from a board view, which is why it had no visible fields: not a missing setting but a different kind of object. The plan had assumed the Roadmap view could be configured the way the Board view is, and the error corrected that before it became a wrong claim in the record.
  - The absence of a grouping parameter is the hard limit of this approach. `updateProjectV2View` sets a name, a layout, a filter, and the visible fields, and nothing else. A timeline needs a date field to be drawn against, and only the human can pick it. The plan says so rather than claiming the view was fixed.
  - The human's second clarification changed the work, and it was the right clarification. "I want to see open and closed issues as well as pull requests" is not a request for a label on a kind of item; it is a request to see every item, in every state, in one place. A kanban board answers that question badly, because it deliberately separates items into columns. The table view is the answer, and it took the reading of a second requirement to see that the first one was a narrower version of the same problem.
  - The built-in date fields on this board are empty. `Created`, `Updated`, and `Closed` all return null for all fifteen items, so the project offers no way to tell an open item from a closed one without the `State` field. This was not visible from the field list, which shows the fields as existing; only reading their values showed that they carry nothing.
  - **Rejected or corrected suggestions:**
    - Rejected: deleting the Roadmap view, which the API allows and which would have left one working view. The human asked for it to be made to work, and a view that is removed is not a view that works.
    - Rejected: creating separate `Issues` and `Pull requests` views with a filter on each. The human chose the `Item type` column over it, and the deciding argument was that the API cannot report which items a view displays, so a filter written through it cannot be verified before the human looks at it.
    - Rejected: renaming the issues so that they no longer match their pull requests. That would rewrite the record of work already done to solve a problem a field solves.
    - Rejected: adding a `Type` field, which is the natural name. The interface has a built-in `Type` column, and a custom field with that name would sit beside it and be indistinguishable. `Item type` cannot collide.
    - Rejected: removing `Assignees` and `Sub-issues progress` from the Board view because both are empty for this repository. Empty is not the same as never needed, and the change commits to being additive.
    - Corrected: the plan was written when the board held eight items, and by the time the change was applied it held fifteen, because the human filed six engine issues and this change's own issue. The plan's current state, scope, acceptance criteria, and work breakdown were updated to the observed count, and the count is no longer asserted anywhere except as a read-back.
    - Rejected: using the built-in `Closed` date field to show which items are closed. It reads as null on every item, open or closed, so it would have been an empty column on the very board it was meant to inform.
    - Rejected: treating the `Status` field as the open-versus-closed signal. `Status` records where a work item sits in the lifecycle, which is a different question from whether the issue is still open on GitHub.
    - Corrected: the plan proposed giving the Roadmap view visible fields that included the date fields. The API refuses that for that layout, and the plan now records the refusal, the name change that was applied instead, and the one manual step the human still owns.
