- **Learning:**
  - The product statement was underspecified in a way that changed the work, and the ambiguity was worth resolving before writing rather than after. "Shell application" could have meant an interactive command shell inside the Rust binary or a POSIX shell script, and the two readings imply different toolchain, testing, and documentation rules. The human chose the interactive shell, which kept section 3's Rust toolchain rule and everything that depends on it intact. A wording choice in a requirements sentence became a structural decision, and it was cheaper to ask than to rewrite the document later.
  - The scope of the change was the second consequential choice. The minimal version would have been two paragraphs in sections 1 and 2, and it would have left section 3's purity rule with no layer permitted to perform I/O, section 4 with no way to test a command, and section 12 silent about what the user is shown. A product statement that contradicts the rest of its own file is a defect, so the consequences were fixed in the same change. The human confirmed that scope explicitly rather than it being inferred.
  - The purest place to put the shell is not in the pipeline. The pipeline in section 2 describes data flow from a source to a combined series, and the shell both consumes that flow and injects commands back into it, so adding it as a fifth stage would have misdescribed the data flow. The document now says the shell wraps the pipeline, which keeps the existing diagram and its four stages intact and still leaves the reader with a way in.
  - Naming example commands was a trap worth noting. A product statement with no example is hard to act on, but a fixed command list would have been a product decision taken by an agent, and section 3 forbids speculative abstraction. The resolution was to name the examples and mark them illustrative in the same sentence, and to add a rule requiring a human decision before an existing command's meaning changes. The examples communicate the shape of the product without being able to harden into an accidental interface.

The same call was issued twice during the investigation; the second call returned the same item id, and the settled board shows a single item, so no duplicate was created.
