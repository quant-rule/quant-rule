## Intent and boundary

Implement the `quantrule.run/v5` reference and identity contract on the
RA-002–RA-004 packs. A run names its model artifact, strategy pack, signal
artifact, portfolio policy pack and execution-simulation pack by id and hash; it
does not duplicate their payloads. This entry covers RA-005 only. The persistent
pack registry (RA-006), signal computation and the strategy service (RA-007,
RA-008), and the client surface (RA-009) remain separate issues.

The loader takes a supplied reference resolver, because the registry that will
hold the bytes does not exist yet. No database, service, new dependency or
client command was added. The execution, portfolio and strategy engines are
unchanged; the run v4 loader and its config hash are unchanged.

## Design decisions for review

- A model artifact's `{id, hash}` is the canonical digest over its
  `(name, sha256)` file entries, matching the diagnostic stage artifact
  identity. The resolver returns the bundle manifest and the loader recomputes
  the digest; it deliberately does not hash the manifest bytes, because a model
  bundle is a file set rather than one JSON object.
- A signal artifact's `{id, hash}` is the SHA-256 of its stored bytes. The
  artifact writer is RA-007, so the loader validates the header and linkage but
  does not canonicalize the rows.
- `model_artifact` is optional for a fold-mode run that computes its model, and
  required when a signal artifact is present. The approved example omitted it;
  the contract now states both cases explicitly.
- The run still requires `output_root`. The approved example omitted it, but
  every existing run uses it and a local v5 run needs a destination.
- The current fold applies sizing, max positions, drawdown, commission and
  funding. `per_trade_risk`, `max_exposure`, `rebalance` and `constraints` are
  validated and retained in `RunV5`, but the portfolio engine does not read
  them yet. Wiring them is an engine change outside RA-005; this is recorded as
  residual risk rather than silently ignored.

## Learning and corrections

- Review found that the first v5 change made `config_files` append the strategy
  file. The model artifact is upstream of strategy, and a strategy-only change
  must reuse the model bundle. The list is restored, and the regression test
  compares the complete model artifact set, not only the file-name list.
- The first model-artifact test compared the reference hash with the manifest
  bytes hash. That conflated a file set with one JSON object; the loader now
  compares the reference with the canonical artifact-set digest and the test
  fixture computes the same value.
- The first signal-fixture pass omitted `bytes` from the model manifest artifact
  entries. The reader now accepts the documented `ArtifactRef` fields rather
  than a narrower pair.
- The data-service scanner had a second copy of the config hash formula. It now
  parses the app loader's `config_hash`, which keeps old hashes identical and
  lets a later v5 scan inherit the reference-aware identity without a second
  implementation.

## Residual risk

The v5 config is not reachable through the catalog, the worker, `run submit`, or
a client command until the persistent registry and signal service land. A loaded
v5 config retains the model and signal artifact references, but no runner
consumes them yet; the model is still computed from the model file and the fold
still decides from the strategy pack. The portfolio policy fields listed above
are retained but not yet applied by the fold. Dataset linkage for a model or
signal artifact remains a submission-time check against the catalog digest; the
config loader checks the artifact's own strategy, model and timeframe links. No
production or edge claim is made by this entry.
