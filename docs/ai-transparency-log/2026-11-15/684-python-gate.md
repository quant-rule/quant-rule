# AI transparency log — DIST-106 gate the product against Python

- Date: 2026-11-15 (UTC)
- Tool: OpenCode with DeepSeek V4.1 Flash.
- Intent: turn the image's no-Python claim into an assertion at source, build,
  and release time, so a reintroduced interpreter or `.py` file fails the gate
  instead of only contradicting the documentation.
- Boundary: `tools/check_python.py`, `tools/test_check_python.py`,
  `docker/check-no-python.sh`, `tools/gate.sh`, the `Dockerfile` assertion,
  the release image-assertion step, the CI checker step, `docker/README.md`
  section 5, `CHANGELOG.md`, and this log. No product Rust semantics, shell,
  web, compose, Makefile, port-parity, or `apps/**` source changed. No new
  dependency, no `unsafe`, no test weakened.

## Implemented

- `tools/check_python.py` exposes `check(root)` and fails on two things: a `.py`
  file outside the governance `tools/` tree and the historical `docs/` tree, and
  an executable `python`/`python3` reference under `crates/`, `apps/`, `docker/`,
  or the `Dockerfile`. The build trees (`target`, `node_modules`, `dist`, and
  the other generated outputs) and the local `data/` root are pruned so a local
  build never decides the gate.
- The interpreter pattern is case-sensitive and token-shaped: `python_number`
  and the prose "an independent Python implementation" do not match, while
  `python3 -m`, `python3.13`, and `apt-get install python3` do. The report names
  the offending path and line.
- Three files are allowlisted with a written reason: `docker/README.md`
  documents the checks, `docker/check-no-python.sh` must name the interpreter it
  rejects, and `apps/web/src/lib/labels.generated.ts` is generated by
  `tools/generate_labels.py` and carries the regeneration command in a comment.
- `tools/test_check_python.py` seeds a `.py` under each product root, a `.py`
  beside the Dockerfile, a Dockerfile install line, a script invocation, a
  versioned interpreter, the governance and history allowlists, the build-output
  exclusions, and an empty tree.
- `docker/check-no-python.sh` is POSIX `sh` (the runtime ships dash). It fails on
  a `python`/`python3` on `PATH`, a `python*` binary in `/usr/bin` or
  `/usr/local/bin`, any `.py` under `/usr`, `/etc`, `/opt`, `/srv`, `/app`,
  `/root`, or `/home`, and a `/tools` directory. It runs in the Dockerfile final
  stage and again from the release image job, so both a tag run and the
  workflow_dispatch dry run assert it.
- `tools/gate.sh` and the CI verify job run the checker; CI also runs the seeded
  test. `CHANGELOG.md` records the gate under `[Unreleased] / Added`.

## Decisions and corrections

- Proposed scanning only `.rs`, `.sh`, and the Dockerfile for interpreter
  references. Rejected: the web client can add a build step just as easily, and
  a narrower scan would miss a `package.json` script that shells out to the
  interpreter. The whole product tree is scanned instead.
- Proposed matching `\bpython\b` case-insensitively. Rejected: it flags the
  legitimate prose in the golden-fixture module docs ("produced by an
  independent Python implementation") and the simulation port notes, which
  describe history and call nothing. The gate matches the lower-case command
  token only, which is the form an interpreter reference takes.
- Proposed a single tree-wide `.py` scan restricted to `crates/`, `apps/`, and
  `docker/`. Rejected: the Docker build context also includes the repository
  root and `config/`, so a `.py` there would enter the image build while passing
  the narrower scan. The scan walks the whole tree minus the two allowlisted
  prefixes.
- Proposed deleting the existing `command -v python3` line from the release
  image-contract step. Rejected: it is a second, independent assertion and the
  new script does not make it wrong. The release job keeps both; the new step
  reports the offending path, which the old one did not.
- The `.py` deletion in the Dockerfile's `apt-get` layer stays. The new script
  is the assertion; the deletion is what keeps the image clean when a base image
  ships pretty-printer scripts.
