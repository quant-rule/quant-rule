# Internal TLS Contract

- Date: 2026-11-23 (UTC)
- Status: Current for the Compose stack, the v2 multi-host profile, and the v3
  Patroni/etcd/HAProxy and RabbitMQ tiers; pgBackRest TLS is HA-013
- Issue: [#1108](https://github.com/quant-rule/quant-rule/issues/1108)
- Claim type: Behaviour Claim
- Related: [ADR](../../adr/2026-11-23/1108-internal-tls.md),
  [security](../../architecture/security.md),
  [HA](../../architecture/ha.md),
  [four databases](../2026-11-22/four-databases.md)

PostgreSQL, RabbitMQ and MinIO use TLS in every deployed profile. Internal HTTP
stays plaintext on the encrypted private overlay. This document is the runtime,
PKI and file-layout contract; it does not claim ingress TLS, mTLS or an HA
failover result.

## 1. Scope and boundary

| Link | Transport | Status |
|---|---|---|
| Client → gateway | HTTPS at the ingress | PLAT-002 (Traefik, cert mode; ACME reserved and refused); the gateway itself serves HTTP |
| Gateway/internal services → PostgreSQL | TLS, `verify-full` | This contract |
| Evidence/backtest → RabbitMQ | TLS on 5671 | This contract |
| Services → MinIO | HTTPS | This contract |
| Service → service | HTTP on the private overlay | Accepted residual risk (section 9) |
| PostgreSQL/RabbitMQ client certificates | none | HA-012 |
| Swarm secret objects, v3 `secrets.files` | none | HA-012 |
| Patroni REST, etcd client/peer, HAProxy | mTLS or basic auth | PLAT-003 (this contract) |
| RabbitMQ broker/front door | TLS-only 5671, shared `rabbitmq` alias | PLAT-004 (this contract) |
| pgBackRest repository TLS | none | HA-013 |

The TLS contract is deliberately ready for Patroni and HAProxy: it names a CA
bundle, a hostname, and a port, so the same client code points at a HAProxy
endpoint or a Patroni primary without a new connector.

## 2. CA model

| Level | Lifetime | Key location | Mounted |
|---|---:|---|---|
| Offline root | 10 years (3650 days) | operator host only | no |
| Online intermediate | 5 years (1825 days) | operator host only | via `ca.crt` |
| Server leaf | 180 days | service-owned volume | yes |

- The root key is generated by `tools/pki.sh` and never leaves the operator
  host. It signs the intermediate only.
- `ca.crt` is the intermediate followed by the root. A client trusts the bundle,
  so a leaf signed by either the old or the new intermediate verifies during an
  overlap.
- The CA private keys stay at mode 600 under `pki/ca/`; only `ca.crt` (mode 644)
  is copied to a service.
- A root compromise requires a new root and re-issue of every leaf. A leaf
  compromise requires a new leaf and a restart; there is no CRL/OCSP responder
  in v1.6.0.
- `PKI_EXTRA_SANS` adds deployment names or addresses, for example
  `10.10.0.20,quantrule.dev`, to every leaf.

## 3. SANs and file layout

Every server leaf carries:

| Type | Value |
|---|---|
| DNS | the service name: `postgres`, `minio`, `rabbitmq` |
| DNS | `localhost` |
| IP | `127.0.0.1` |
| DNS/IP | every `PKI_EXTRA_SANS` entry |

`tools/pki.sh --out DIR` writes:

```text
DIR/
  ca.crt                      intermediate + root bundle (644)
  ca/root.crt root.key        offline root (key 600)
  ca/intermediate.crt .key    online intermediate (key 600)
  postgres/server.crt .key    key 600, cert 644
  postgres/ca.crt             copy of the bundle
  rabbitmq/server.crt .key
  rabbitmq/ca.crt
  minio/public.crt            MinIO server certificate
  minio/private.key           MinIO server key (600)
  minio/CAs/ca.crt            MinIO trust bundle
```

The directory is mode 700, certificates 644, keys 600. `make pki` writes
`./pki`; `FORCE=1 make pki` regenerates the directory and therefore invalidates
every mounted copy until the stack restarts.

The Compose `pki-init` one-shot runs as root, copies each mounted certificate
into a named volume owned by the service UID, keeps the key at 0600, and exits.
PostgreSQL, RabbitMQ and MinIO still start as their stock non-root users. The
database is never run as root and a Postgres key is never chmod-ed to 0644.

## 4. PostgreSQL

Server (Compose and v2 infra):

```text
ssl = on
ssl_cert_file = /var/lib/postgresql/pki/server.crt
ssl_key_file  = /var/lib/postgresql/pki/server.key
ssl_ca_file   = /var/lib/postgresql/pki/ca.crt
ssl_min_protocol_version = TLSv1.2
```

Client:

| Item | Rule |
|---|---|
| URL | `postgres://role:password@host:5432/db?sslmode=verify-full` |
| CA | `QR_DATABASE_TLS_CA_PATH`, absolute, read once at pool open |
| Mode | `verify-full` only; `prefer`, `require` and `verify-ca` are refused |
| Client cert | none; the server does not request one |
| Failure | pool open error, `/ready` degraded, migration job fails |
| Fallback | none; a missing CA or handshake failure never becomes plaintext |

The one-shot `<service>-migrate` job uses the same CA path. `db-bootstrap` sets
`PGSSLMODE=verify-full` and `PGSSLROOTCERT`. The healthcheck stays on the local
Unix socket and does not need TLS.

## 4.1 Patroni, etcd and HAProxy

`tools/pki.sh` issues the stateful leaves under the same internal CA. The
renderer copies them to `out/pki/` and lists them in `stateful-manifest.json`.

| Link | Transport | Rule |
|---|---|---|
| Patroni -> etcd | HTTPS on 2379 | `etcd/client.crt` + key, `cacert`; server verifies the client against the CA |
| etcd peer | HTTPS on 2380 | `etcd/peer.crt` + key; `client-cert-auth: true` |
| etcd client listener | HTTPS on 2379 | `etcd/server.crt` + key; `client-cert-auth: true` |
| Application -> PostgreSQL | TLS on 5432, `verify-full` | HAProxy passes TCP through; the server leaf carries `postgres` and every `patroni-<host>` SAN |
| Patroni REST | HTTP on 8008 with basic auth | HAProxy sends the header read from `patroni_rest_password`; the password is not in the rendered config |
| HAProxy frontend | TCP on 5432 | No TLS termination, no published port; stats on the overlay only |

The Postgres leaf is one certificate deployed on all Patroni nodes. Its DNS SAN
must include `postgres` and every `patroni-<host>`; `PKI_EXTRA_SANS` supplies the
latter so replication and pg_rewind can use `verify-full` against the overlay
alias. The etcd server and peer leaves must include every `etcd-<host>`; the
client leaf has `clientAuth`. A key is mode 600; a certificate is 644. There is
no plaintext etcd listener and no HAProxy TLS termination. The stateful check
rows query these leaves through `QR_DEPLOY_OPENSSL`, and the lab `psql` uses
`verify-full`; a live etcd/Patroni handshake and the failover remain lab
evidence. The exact sample set is in the
[Patroni cluster contract](patroni-cluster.md#5-tls).

## 5. RabbitMQ

Server (`rabbitmq-<host>.conf` in v3; `deploy/rabbitmq/rabbitmq.conf` in Compose):

```text
listeners.tcp = none
listeners.ssl.default = 5671
ssl_options.cacertfile = /var/lib/rabbitmq/pki/ca.crt
ssl_options.certfile   = /var/lib/rabbitmq/pki/server.crt
ssl_options.keyfile    = /var/lib/rabbitmq/pki/server.key
ssl_options.verify = verify_none
ssl_options.fail_if_no_peer_cert = false
ssl_options.versions.1 = tlsv1.2
ssl_options.versions.2 = tlsv1.3
```

The v3 unit copies the leaf from `/etc/quantrule/pki/rabbitmq` into
`/var/lib/rabbitmq/pki` with the broker owner before it starts. There is no
plaintext listener, no management listener, and no published port. The leaf
covers `rabbitmq` plus every `rabbitmq-<host>`; `PKI_EXTRA_SANS` supplies the
unique broker names. The Erlang distribution between brokers is not TLS in
v1.6.0: it uses the encrypted overlay and is a separate issue. The queue check
rows verify this listener, the broker leaf SAN/expiry, and the HAProxy
`rabbitmq:5671` front door; `tools/queue-definitions.sh` strips users and
permissions before storing topology.

Client:

| Item | Rule |
|---|---|
| URL | `amqps://qr_queue:password@rabbitmq:5671/%2f` |
| CA | `QR_QUEUE_TLS_CA_PATH`, absolute, re-read on reconnect |
| Client cert | none (`verify_none`, `fail_if_no_peer_cert=false`) |
| Topology | quorum queues, delivery limit 3, DLX and the generation suffix are unchanged |
| Front door | HAProxy TCP `rabbitmq:5671` on the edge pair; brokers use `rabbitmq-<host>` only |
| Failure | connection fails; the consumer rebuilds it from the stored URL/CA; no plaintext retry |

## 6. MinIO

Server: the image starts with `MINIO_SCHEME=https` and `--certs-dir /certs`,
where `/certs` contains `public.crt`, `private.key` and `CAs/ca.crt`. The
healthcheck trusts `CURL_CA_BUNDLE=/certs/CAs/ca.crt`.

Client:

| Item | Rule |
|---|---|
| URL | `https://minio:9000` with no userinfo |
| CA | `QR_OBJECT_STORE_TLS_CA_PATH`, absolute |
| Trust store | explicit Smithy `TrustStore::empty()` plus the bundle; platform roots are not used for the private endpoint |
| Credentials | the two `_FILE` values; no `aws-config` and no AWS default chain |
| Addressing | path style, region `us-east-1` |
| Failure | client construction or handshake fails; no plaintext retry |

## 7. Configuration

| Variable | Owner | Notes |
|---|---|---|
| `QR_DATABASE_TLS_CA_PATH` | gateway, data, evidence, simulation and their migration jobs | required with `verify-full` |
| `QR_QUEUE_TLS_CA_PATH` | evidence, backtest | required with `amqps://` |
| `QR_OBJECT_STORE_TLS_CA_PATH` | data, model, strategy, evidence, simulation, backtest | required with `https://` |
| `QR_PKI_DIR` | Compose only | host directory mounted at `/run/pki` |
| `QR_PKI_*_UID` / `QR_PKI_*_GID` | Compose `pki-init` only | override the stock service UIDs |

The three CA paths are not secrets. They appear in `Config` debug output and in
a startup error. A relative path, empty value, TLS scheme without a CA, or CA
beside a plaintext scheme is a startup error.

## 8. Rotation

1. Issue a new intermediate or leaf with `tools/pki.sh` (or the operator CA).
2. Replace the bundle and leaf on the operator host. The old and new
   intermediate are both in `ca.crt` during the overlap.
3. Restart `pki-init` and the affected service with a rolling restart. `/ready`
   flips to `503` before the process stops; the other replica serves.
4. Verify a handshake and the canonical digest, then remove the old
   intermediate from the bundle in a second restart.

A leaf is valid for 180 days; rotate at 30 days remaining. A CA bundle is
overlapped for at least one rolling restart. A missing or stale bundle fails
closed. The root key is not rotated on the leaf schedule.

## 9. Internal HTTP residual risk

Internal service-to-service calls stay `http://` on the encrypted private
overlay. The deployment accepts these consequences explicitly:

- A compromised overlay host can impersonate any service and read
  inter-service traffic.
- The profile header (`X-QuantRule-Profile`) remains trusted because the
  network is trusted; a peer that can reach an internal service can set it.
- The gateway bearer token is the only human authentication. Internal services
  have no application authentication.
- A database or object-store credential leak is still limited by the
  per-service roles and the file-backed secret contract, not by mTLS.
- The runtime does not add an HTTPS connector to `client/http.rs`; doing so
  would not authenticate a client and would create a second TLS stack without a
  service identity.

Compensating controls: encrypted overlay, no published internal port,
`QR_INTERNAL_ONLY`, per-service database roles, file-backed secrets, the gateway
token, and the network firewall. The Security and Privacy Reviewer accepted
option B with this residual risk; human acceptance remains the final gate.

## 11. Failure and verification

| Symptom | Cause | Action |
|---|---|---|
| `QR_DATABASE_TLS_CA_PATH is required` | `verify-full` without a CA | add the path or fix the URL |
| `must use sslmode=verify-full` | `prefer`, `require` or `verify-ca` | rewrite the URL; do not weaken the mode |
| `amqps:// requires QR_QUEUE_TLS_CA_PATH` | missing queue CA | mount the bundle |
| `cannot read the object-store CA bundle` | missing or unreadable file | fix the mount; do not fall back to HTTP |
| `stateful ... certificate ... does not cover` | A Postgres/etcd leaf lacks an overlay alias | Re-issue with `PKI_EXTRA_SANS`; never weaken `verify-full` |
| `queue ... rabbitmq certificate ... does not cover` | The RabbitMQ leaf lacks `rabbitmq` or a broker alias | Re-issue with `PKI_EXTRA_SANS=rabbitmq-<host>,…` |
| Pool opens but `/ready` is degraded | the database rejected the handshake | check SAN, expiry and CA |
| `pki-init` exits non-zero | `make pki` was not run or the mount is wrong | run `make pki`, restart the stack |

Fast evidence: `cargo test -p quantrule-runtime` (config pairing, S3/RabbitMQ
seams, `rcgen` success/wrong-CA/hostname/expiry fixture) and
`cargo test -p quantrule-deploy` (descriptor, render, queue rows, definitions).
`make compose-check` validates both Compose files with a disposable PKI and
`docker compose config -q`. Composed handshakes and CA overlap remain later
evidence; the Patroni/etcd/HAProxy paths are rendered, and a live handshake is
lab evidence. `pitr: true` and the archive knobs are configured, not verified.
