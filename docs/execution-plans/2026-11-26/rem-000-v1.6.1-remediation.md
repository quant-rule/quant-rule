## 1. Intent

Close the gap between what `v1.6.0` claims and what the repository demonstrably
does, without moving the published `v1.6.0` tag:

1. Make `quantrule.run/v5` executable end to end, including production
   resolution of the model artifact, strategy pack, signal artifact, portfolio
   policy pack, and execution-simulation pack.
2. Write run lineage at submission, atomically with the run row, so
   `run lineage` is a real producer/consumer path rather than a read-only stub.
3. Close or explicitly accept the HA, soak, upgrade, remote-client, security,
   and signature evidence gates.
4. Correct the record: the old plan, the release note, the architecture status
   lines, the HA matrix, and the board must agree with the evidence.
5. Keep the product research-only. No live trading, no broker, no edge claim,
   no statistical signal path, and no change to the meaning of the 61 commands.

The result is a release that can honestly say either “all remediation gates
passed” or “these named gates are accepted risks”, with the evidence attached.

## 3. Scope

Included:

- Run-v5 production resolution at submission and in the worker, with hash
  verification, fail-closed behavior, and no per-bar network call.
- Atomic run-lineage write at submission; idempotent repeat; refusal of a
  different reference set; `run lineage` read path.
- v4 compatibility and the 49 pre-RA command meanings unchanged.
- Strategy-service replica-kill evidence (V09).
- 72-hour soak harness and run.
- Versioned rolling upgrade and rollback from `v1.6.0` to `v1.6.1`.
- Real HA (HA-22/HA-23): single-laptop accepted risk with the release-note
  boundary; no Real HA claim.
- Remote client RR-07: local client over loopback/private CA, or accepted risk
  for a second-machine client; no remote claim without a second machine.
- Independent Quant Validator and independent security review, or a disclosed
  sequential pass with human acceptance.
- Image signature, SBOM, CVE refresh, release candidate, release note, changelog,
  annotated tag, post-release verification, and rollback drill.
- v1.5.3 disposition, old-plan closure, architecture status lines, HA matrix,
  research-readiness record, board, worktrees, and AI logs.
- Two structural decisions: MinIO replication vs off-host archive, and a pure
  `quantrule-strategy` crate vs `quantrule-app::signal`.

Excluded:

- Live trading, broker connectivity, OMS, real-time risk, or regulatory scope.
- New alpha, a new model event, a strategy hypothesis, or an edge claim.
- Statistical, fitted, machine-learning, or neural-network signal generation.
- Desktop shell, Tauri, installers, OS packages, Python, Kubernetes, accounts,
  tenancy, or autoscaling.
- A fifth database, four separate PostgreSQL clusters, or a per-bar network fold.
- Moving, deleting, or reusing the published `v1.6.0` tag.
- Reopening a `Done` board item. Remediation is new issues that link back.

  second machine, and no second failure domain. HA-22/HA-23 are therefore
  `Accepted risk` paths; the release note must say `Simulated HA`, not
  `Real HA`. The three-VM lab may run on the laptop only if capacity allows, and

- The offline cosign private key is not present on the laptop and no `cosign`
  binary was found. The signature is `Accepted risk` unless the operator
  supplies both; the release note says `pending`, not signed.
- The 72-hour soak can run continuously for 72 hours on the laptop if the
  capacity preflight passes. A preempted run is restarted from zero; partial
  hours are not a 72-hour soak.
- The laptop currently reports 8 CPUs, about 0.8 GiB available RAM, and 179 GiB

  is a gate, not a formality. If the stack cannot run for 72 hours, stop and
  report instead of claiming a shorter soak.
- A separate agent/model or a human reviewer is available for the independent
  Quant and security passes. If not, the sequential pass is disclosed and the
  human records the acceptance.
- The run-v5 resolver can be added without a new database or a per-bar service
  call. The design is an ADR gate; if it requires a new stateful system, stop and
  return to the human.
- The published `v1.6.0` image remains available for rollback at

## 6. Release definition of done

`v1.6.1` is done only when all of the following are true:

- A `quantrule.run/v5` submitted through the gateway resolves all five
  references by ID and hash, creates one run, writes lineage atomically,
  executes, publishes artifacts, and returns a canonical digest.
- `run lineage <run_id>` returns the five references; a repeated identical set is
  idempotent; a different set is refused; a missing object or mismatched hash
  fails closed before a run row is created.
- A v4 run still loads, executes, and produces the same digest as before.
- The strategy service survives a replica kill with one retry, one signal
  artifact, and no partial publish (V09).
- The laptop capacity preflight passes and a 72-hour soak completes with no
  health failure, no queue backlog that does not drain, no memory/disk leak, and
  a stable canonical digest. If the preflight fails, stop; do not claim a shorter
  soak.
- A rolling upgrade from `v1.6.0` to `v1.6.1` completes with an active run, no
  partial publish, and the same digest; rollback to `v1.6.0` succeeds.
- HA-22 and HA-23 are `Accepted risk` with a single-laptop record and a
  release-note boundary; no Real HA claim is made.
- RR-07 is `Accepted risk` for a second-machine client, or is verified only as a
  local client over loopback/private CA and labelled accordingly.
- The image signature is `Accepted risk` because the key and `cosign` binary are
  absent; the release note says `pending`, not signed.
- Independent Quant Validator and independent security review records exist, or
  the sequential passes are disclosed and accepted.
- `qr-governance check --all` passes; docs, code, commands, and tests agree.
- The old plan is `Verified` with accepted exceptions or `Superseded`; V01, V09,
  V18, V20, and V21 each have a final status.
- The board is consistent; merged worktrees and local/remote branches are
  removed; no board item is deleted.
- No Critical audit finding is open on the changed path.
- The release note states the evidence boundary honestly; no `Real HA`, 72-hour
  soak, versioned-upgrade, or signed-image claim is made without evidence.

## 13. Release and rollback runbook

1. Freeze the v1.6.1 candidate commit and data/config fixtures.
2. Run `tools/gate.sh`; run `make up` and `tools/test_tiers.sh composed`.
3. Build one `linux/amd64` image; record the staging digest.
4. Generate the SPDX SBOM; run Grype and `cargo audit`; fixable High and any
   Critical fail.
5. Push the version image only after the scan; verify the digest equals staging.
6. Run the composed tier, the v5 E2E, the strategy kill, the upgrade, and the
   remote client against the candidate.
7. Run the 72-hour soak; a preempted run restarts from zero. A shorter soak is a
   scope change, not an accepted version of this gate.
8. Record the single-laptop `Accepted risk` for HA-22/23 and RR-07; do not run
   the real-host gate.
9. Sign the exact digest offline if the key and `cosign` exist; otherwise record
   the signature `Accepted risk`. If signed, run `tools/release.sh verify`,
   bundle, attach the SBOM, CVE report, bundle, and signed image, and record the
   hashes.
10. Write the release note, changelog, and old-plan addendum; run
    `qr-governance check --all` and `qr-governance release note --tag v1.6.1`.
11. Merge the release PR; create the annotated `v1.6.1` tag from `main`; publish
    the GitHub release.
12. Verify the release through the gateway; run the rollback drill; record the
    evidence.
13. Remove the worktrees and local/remote branches; keep the `Done` board items.

Rollback: the previous image is `v1.6.0` at
`sha256:a000bce9c5de62d6dbc9c81786aff01ce894d9d3bfcfbd69eb64be8e483e3b4f`.
Migrations are forward-only; restore the pre-upgrade backup and the previous
image, return DNS to the old endpoint, rebuild the queue, and verify the
canonical digest. v5 submission has a fail-closed kill switch: if resolution is
unavailable, `run submit` rejects v5 with a stable config/service error; v4 runs
continue.

## 15. Stop conditions

Stop and request human direction when:

- The plan needs a new claim type, scope, dependency, database, or architecture
  decision.
- ADR-RA-2 would require a new stateful system or a per-bar network call.
- A v5 change would alter a v4 result or a signal value.
- A verification row fails and the fix changes the approved scope.
- Real HA hardware, the offline key, or an independent reviewer is unavailable
  and the human has not recorded an accepted risk.
- A test would be weakened, skipped, or deleted to obtain a pass.
- A digest mismatch, partial publish, cross-DB inconsistency, or Critical
  security finding appears.
- The board, old plan, release note, and repository evidence disagree.
- A published tag, a Done board item, or a user worktree would be moved,
  reopened, or deleted.
- Git authorization is missing for a commit, push, PR, merge, tag, or cleanup.
