## Intent

The three Progression goldens were originally produced by an independent
Python replay that was never checked in. #196 changed the published-leg rule
and regenerated the affected fixture values from the Rust implementation. The
fixtures are therefore temporarily self-referential: a regression in the
Progression state machine would move the expected values with it.

This work rebuilds that replay as a checked-in tool, reproduces the current
fixtures from `readings_golden.csv`, and removes the temporary-independence
exception from the fixtures and their test modules. It does not change the
Progression contract or any production Rust code.

Affected users: maintainers who rely on the Progression goldens to detect a
model regression, and reviewers of any future Progression change.

## Scope

Included:

1. A pure Python state machine in `tools/oracle/progression_model.py` that
   implements leg creation, confirmation, completion, supersession,
   invalidation, target selection and revision, target stability, progress,
   stage, publication, readiness, reason, percentile, and state counters from
   contract §8.4/§9 and D1–D10.
2. A CLI in `tools/oracle/progression_replay.py` that reads
   `crates/quantrule-model/tests/fixtures/readings_golden.csv` and renders:
   - `progression_golden.csv` and `progression_legs_golden.csv` in full;
   - the `axis_code 4` rows of `dashboard_readings_golden.csv`;
   - the Progression lines of `market_report_golden.txt`.
   The non-Progression rows and lines are preserved byte for byte from the
   existing fixtures, which were independently generated by earlier replays.
   `--check` compares the rendered files with the checked-in ones and exits
   nonzero on any difference; `--write` regenerates them deliberately.
3. A stdlib `unittest` suite in `tools/oracle/test_progression_model.py` for the
   state machine, publication rule, target revision, stability, stage,
   percentile, and counters.
4. Fixture headers and test module docs updated to name the checked-in oracle
   and its inputs, and to remove the #196 temporary-independence exception.
5. `tools/oracle/README.md` with the command, inputs, outputs, and check/write
   workflow; a short link from `docs/README.md`; and Python bytecode ignores in
   `.gitignore`.
6. A CI step that runs the oracle unit tests and `--check`, so the fixtures
   cannot silently drift from the replay again.

Excluded:

- No change to the Progression contract, the Rust state machine, or any
  published value. The replay must reproduce the current fixtures.
- No full replay of the other axes' dashboard rows or report lines. Those parts
  were independently generated by the #122 and #150 replays and are preserved
  unchanged; this work restores independence only for the Progression-derived
  content.
- No new Rust crate, Python package, or network access.
- No shell command. The oracle is a developer tool, not a product surface.
- No fixture regeneration by `--write` as part of the final change; the
  checked-in files must already match.

## Assumptions and uncertainty

- The current fixtures are the expected output. A mismatch is investigated as a
  defect in the oracle or in the Rust implementation; a fixture is never
  changed merely to make `--check` pass.
- The oracle can reproduce the Python `str(float)` representation in the
  checked-in CSVs if the arithmetic order matches the contract. If a value
  differs only in the last bits because of operation order, the order is
  aligned to the contract and the difference is explained; it is not hidden
  behind a loose tolerance.
- The author has read the Rust implementation while investigating #196 and this
  issue. The replay is therefore not blind to the code under test. It is
  implemented from the contract and D1–D10, with the Rust read only to resolve
  ambiguities those documents already record. The limitation is recorded in
  the transparency log, and the reviewer checks the oracle against the contract
  rather than against the Rust code.
- The report's chart bucket boundaries can be read from the existing fixture
  (`first`/`last` per `chart_bar`), so the oracle does not re-derive the chart
  geometry. The `stage` value is the last non-null stage in the bucket.

- `python3 -m unittest discover -s tools/oracle -p 'test_*.py'` passes.

  describe the Progression values as temporarily non-independent; they name
  the oracle and its input.
- The checked-in fixtures are byte-identical to the pre-change files except for
  their comment headers.
- No production Rust source file changes. `cargo test` still passes 1,350
  tests, and the golden tests still compare the same values.
- `cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`,
  and `cargo doc --no-deps` pass.
- CI runs the oracle tests and `--check` (if D4 is approved).
- The replay is deterministic: two consecutive `--check` runs produce the same
  result, and `--write` followed by `git diff` leaves the fixtures unchanged.

## Risks and recovery

- **A real Rust defect is found.** Stop, record the mismatch, and request a
  separate fix; do not regenerate the fixture around it. Recovery is the revert
  of this branch.
- **The oracle is a translation of Rust rather than a contract replay.** The
  reviewer compares the oracle to §8.4 and D1–D10; the limitation is recorded.
  If it cannot be established, stop rather than claim independence.
- **Float representation differs.** Investigate the operation order; do not
  replace the byte comparison with a loose tolerance unless the human approves
  that weaker contract.
- **CI Python availability.** `ubuntu-latest` provides `python3`; if the runner
  does not, remove the CI step and keep the local command documented.
- **Accidental regeneration.** `--check` is the default; `--write` is only used
  deliberately, and the resulting diff is reviewed.

## Stop conditions

- Any fixture data value differs from the current checked-in value.
- A Rust production change appears necessary.
- The oracle cannot be shown to follow the contract rather than the Rust code.
- The CI change is rejected or the runner cannot execute the oracle.
- A new dependency, a contract change, or a fixture value change would be
  required.
